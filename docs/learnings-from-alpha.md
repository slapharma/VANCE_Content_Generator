# Learnings from alpha (vancecontent → Beta)

Append-only log of project-specific learnings, fixes, gotchas, and architectural notes from working on **vancecontent** (alpha) that should reach **Beta** (CliftonAi-Content, project `SCF-Multi-Agency`) and downstream brand iterations.

## How this works

This file rides the ship pipeline. Every time alpha's `main` is merged into Beta's `main`, this file flows with it. Beta-side sessions reading their own project root will find this file in `docs/learnings-from-alpha.md` and pick up everything that landed since the last ship.

**Scope**: project-specific learnings only. Universal learnings (Windows path quirks, tool gotchas) go to `~/.claude/lessons.md` which is global. The split rule:

- Specific to vancecontent's architecture, schema, prompts, deploy, KV layout, or Vance-the-brand → here.
- Applies to *any* project I open → `~/.claude/lessons.md`.

When in doubt: prefer this file. False positives here are cheap (Beta gets a slightly off-topic note). False negatives in the global file are expensive (the same mistake gets re-made on another project).

## 2026-07-27 — A scheduled-post queue is only as precise as the cron that drains it

- **Context**: Wiring per-rule carousel posting (`immediate` / `delay X hours` / `optimal slot` / `hold for approval`) into the automation rules.
- **Finding**: Two things that only surface once you look at the whole path from "pick a time" to "post goes out":
  1. **`social:queue` was drained once a day** (`/api/social/cron` on `0 9 * * *`), so nothing finer than daily could ever be honoured. A "delay of 3 hours" would silently round to the next 09:00 tick. Worse, this was **already breaking existing kit scheduling**: `autoSchedule` picks 07:00/12:00/19:00 slots, so a 19:00 slot had always fired at 09:00 the *next day* — 14 hours late — and nobody would see it as a bug because the post did eventually go out. Fixed by draining hourly (`0 * * * *`); Vercel Pro allows arbitrary cron expressions. **Whenever you add scheduling precision, check the drain interval first** — the queue's granularity is the cron's granularity, not the timestamp's.
  2. **Anchor automatic social posts to the article going LIVE, not to generation.** The carousel is built during the run, but on a review-required rule the article is not published until approval. Scheduling from generation would let a carousel post while its "READ THE FULL ARTICLE" slide and caption deep link still pointed at nothing. So the run applies the schedule only when `!rule.review.required`, and `approve.js` applies it otherwise — two code paths, one shared `applyPostMode()` so they cannot drift.
  Also worth noting: `lib/automation/handlers/rules-id.js` PATCHes with `{...rule, ...body}` and **no** `buildRule()` validation, so rules saved before a new `generation.*` field exists simply lack it. Every consumer therefore needs the same literal fallback (`?? 'approval'` in three places here) — the schema default alone does not backfill existing records.
- **Implication for Beta**: The hourly social cron is one of Beta's shared crons — under multi-tenancy a single hourly drain serving every tenant will need either batching or per-tenant queues, and the 40-cron Vercel cap means it cannot be one cron per tenant. Also: `carouselPostMode: 'immediate'` publishes publicly with no human in the loop, which is a very different risk profile on an agency platform than on a single owner-operated brand — Beta should probably restrict the non-`approval` modes by tenant role, and must keep the default at `approval` so no tenant inherits hands-off posting.
- **Tag**: #deploy #social #wizard

## 2026-07-27 — WP media never overwrites, so anything that re-renders images must delete its own orphans

- **Context**: Adding the category tag / logo / copy changes to the carousel slides meant re-rendering existing decks. Each re-render produced `…-1.jpg`, then `-2`, then `-3`.
- **Finding**: WordPress does not overwrite media on re-upload — it suffixes. Any feature that re-generates and re-uploads images therefore leaks N files per run (8 per carousel here) unless it explicitly deletes what it replaced. Added `deleteWpMedia(ids)` (`?force=true`, since media cannot be trashed) called after the new slides are committed, diffing old vs new `mediaId`s.
  Two traps hit while verifying it:
  1. **I first guarded cleanup behind `!carousel.postedAt`**, assuming deleting the source would break a live Instagram post. That is wrong: the Graph API *downloads* `image_url` at publish time and serves its own copy from Instagram's CDN, so the WP file is only ever the source of that one fetch. The guard just leaked files for every posted deck.
  2. **A deleted image still returned HTTP 200** — the site is LiteSpeed with `Cache-Control: public, max-age=604800`, so the URL stays served from cache well after the attachment is gone. Verifying a deletion needs a **cache-busting query string**; without one you will conclude the delete failed when it succeeded. Confirm via the API's own reported count, not by fetching the URL.
  Also: when a platform's log API is unreachable (Vercel's returned 403 here), returning the housekeeping result **in the endpoint's own response** is a far faster diagnostic loop than chasing logs.
- **Implication for Beta**: Any tenant-facing feature that re-uploads derived images (carousel slides, regenerated heroes, thumbnails) needs the same delete-the-superseded step, or tenant media libraries grow without bound — and on a shared/multi-tenant host that is a real storage-cost and quota problem, not just untidiness. Worth adding a periodic orphan sweep per tenant (list carousel-prefixed media, drop anything no live carousel record references), because any interrupted render still leaks. Note the delete needs the tenant's WP user to hold `delete_posts`; a contributor-level app password will fail with a capability error, which is why `deleteWpMedia` returns the response body rather than just the status.
- **Tag**: #deploy #kv #social

## 2026-07-27 — Composio does NOT mirror the raw Instagram Graph carousel flow (it has its own tool)

- **Context**: The first live "Post now" on an Article Carousel silently degraded to a cover-only single image. Runtime logs gave the real cause.
- **Finding**: I had assumed Composio's `INSTAGRAM_CREATE_MEDIA_CONTAINER` mirrored the Graph API's carousel flow (child containers with `is_carousel_item: true`, then a parent with `content_type: 'carousel'` + `children`). **It does not.** The actual error:
  ```
  Invalid request data provided
  - Input should be 'photo', 'video', 'reel' or 'carousel_item' on parameter `content_type`
  ```
  Two corrections:
  1. The child enum value is **`carousel_item`** — not `'photo'` plus an `is_carousel_item` flag, and there is no `'carousel'` value at all.
  2. Composio has a **dedicated `INSTAGRAM_CREATE_CAROUSEL_CONTAINER`** tool which accepts **`child_image_urls`** directly, so it creates the child containers itself. That collapses the flow from 9 calls to **2**: create the parent container with the slide URLs + caption, then `INSTAGRAM_POST_IG_USER_MEDIA_PUBLISH` with its `creation_id` (that publish tool auto-polls for FINISHED, so no manual status loop).
  Also: `INSTAGRAM_POST_IG_USER_MEDIA_PUBLISH` documents `'me'` as an acceptable `ig_user_id`, but `INSTAGRAM_CREATE_CAROUSEL_CONTAINER` wants the **numeric** Business Account id — so `'me'` is not a safe universal default. Resolve it via `INSTAGRAM_GET_USER_INFO` (`data.id`) when the account record has none. And note `lib/social/composio.js`'s `executeTool` already unwraps to `res.data`, so ids arrive at `out.id`, not `out.data.id`.
  **Verification trick worth reusing**: creating a media container is a *private draft*, so the whole call chain can be validated with a real deck **without publishing anything**. Containers expire in under 24h on their own. This is the only safe way to test an irreversible public action.
  **Trap that cost me a wrong conclusion**: an MCP/claude.ai Composio connector is a *different Composio workspace* from the one the deployed app uses (the app has its own `COMPOSIO_API_KEY` + `COMPOSIO_USER_ID`, and its own account registry in `social:accounts:*`). Reading connected accounts through an MCP session told me the Instagram account was `@merlowsnews` when the app was in fact posting to `@vancehealthhub` — I reported a brand mismatch that did not exist. The app's own registry (`GET /api/social/accounts`) is the only authority on which account it posts to; a container created via MCP also lands on the *MCP-side* account, so that dry run verifies the tool contract but not the app's connection.
  Confirmed by that dry run: 1080×1350 JPEGs hosted on the WP domain are accepted (Composio's schema wants JPEG, aspect between 4:5 and 1.91:1, width 320–1440px, ≤8 MB — 4:5 sits exactly on the lower bound and passes).
- **Implication for Beta**: Beta shares `lib/social/platforms/composio.js` and its `SLUGS` map, so it inherits the same wrong assumption anywhere carousels are added — use `INSTAGRAM_CREATE_CAROUSEL_CONTAINER`, not the generic container tool. More generally: **the `// VERIFY-LIVE` slugs and argument shapes in composio.js are guesses until exercised**, and the Graph API's shape is a poor predictor of Composio's — always introspect the real schema (`COMPOSIO_SEARCH_TOOLS` / `COMPOSIO_GET_TOOL_SCHEMAS`) before writing the call. For multi-tenancy, each tenant's connected account needs its own resolved numeric `ig_user_id` cached on the account record, since the extra `INSTAGRAM_GET_USER_INFO` round-trip per post adds up. Finally: a degraded-post flag must be **assigned** (`degraded: !!result.degraded`), never spread-when-true, or a successful retry can never clear it.
- **Tag**: #social #composio #deploy

## 2026-07-27 — Article Carousel: server-side image compositing arrives (satori + resvg + jpeg-js)

- **Context**: Added **Article Carousel** — an 8-slide 4:5 educational Instagram carousel built automatically from each generated article, opted into per rule (`generation.articleCarousel`, default **false**). New Social ▸ Carousels pane for review/edit/re-render/approve. This is the project's first server-side image compositing of any kind.
- **Finding**: Several things that will bite anyone repeating this:
  - **The stack**: `satori` (layout) → `@resvg/resvg-js` (SVG→RGBA) → `jpeg-js` (RGBA→JPEG). satori accepts plain `{type, props}` objects, so **no JSX and no build step** — which is why it fits this project. satori **outlines every glyph to `<path>`**, so resvg never needs font access; the only font data in the pipeline is the two base64 faces in `lib/social/fonts/montserrat.js`. JPEG is **not optional**: Instagram's Graph API requires `image_url` to be JPEG and resvg only emits PNG.
  - **Fonts must be base64 in a `.js` module**, not `.ttf` on disk. Vercel's bundler does not reliably trace runtime `fs` reads, so a repo `.ttf` can vanish from the deployed bundle. A plain `import` is always bundled and needs no `vercel.json` `includeFiles`. Latin-subset via `pyftsubset` takes Montserrat from 450 KB → 35 KB per face (`scripts/build-carousel-fonts.mjs` regenerates).
  - **Effective size, not nominal**: a 1080px slide renders at ~400 CSS px in a phone feed, so everything shrinks ~2.7×. A "34px" caption is ~12.6px to the reader. All *content* text is ≥44 slide px to clear a 16px effective floor. Sizing by nominal px produces an unreadable deck that looks fine in a preview.
  - **`#006868` cannot be a text ground.** White on `--vance-primary` measures 6.60:1 — AA but never AAA, and *no* alpha tint over it reaches 7:1. Dark grounds must be `--vance-dark #1b3355` (white = 12.72:1). Also: white on `--vance-accent #4DBDBD` is **2.25:1** and fails outright, so accent can never be a button fill; and a tinted "ghost" numeral measured 1.17:1 (invisible at thumbnail size) and had to become a solid ink chip. Ratios are recorded inline in `lib/social/carousel-theme.js`.
  - **satori layout trap**: `justifyContent: 'center'` on the outer column *plus* a `flexGrow` spacer before a footer fights itself — the spacer wins and every slide comes out top-heavy with a dead bottom third. Let the *content block* grow and align internally (`slideFrame` in `carousel-render.js`). satori also collapses consecutive whitespace, so footer alignment must come from `space-between`, not padded spaces.
  - **Photo scrims need to be near-opaque under text.** A mid-strength scrim let the cover headline cross a brightly lit surgical glove and lose its contrast. Scrims are now per-slide `[position%, opacity]` stop lists that spend transparency only where nothing is written.
  - **Architecture**: a carousel is a **first-class KV record** (`social:carousel:{id}`), not part of a social kit — kits are user-initiated and cost 6 LLM calls, carousels are automation-initiated and cost 1, and separating them lets a Reel and a carousel coexist for one article on different schedules. Posting reuses the kit queue (`social:queue` / `social:postref:*`) with `kind: 'carousel'`; refs **without** `kind` are kit posts, which is every pre-existing ref.
  - **Slides are hosted in the WP media library**, because the Graph API fetches `image_url` itself and a media upload needs no post to exist — which matters since review-path carousels are built before the article is published. `uploadHeroImageToWp` in `api/publish` was refactored onto the shared `lib/social/wp-media.js` for this.
  - **Keep the heavy deps out of other functions.** `run.js` triggers the carousel over HTTP (like it already does `/api/publish`) so satori/resvg never enter the automation bundle, and `carousel.js` imports the renderer **lazily** so `/api/social/deploy|cron|connections|accounts` don't pay it at cold start. Verify with an import-graph trace after any refactor — a stray static import silently undoes both.
  - **Instagram caps carousels at 10 children** (not the 20 the app allows). 8 is the default; `assertPostableSlideCount` hard-errors outside 2..10 rather than truncating.
  - Composio's `INSTAGRAM_CREATE_MEDIA_CONTAINER` carousel support is **still unverified** (`// VERIFY-LIVE`); the direct Graph API path is preferred when its env vars are set, and the Composio path degrades to a cover-only single image with a logged warning.
- **Implication for Beta**: The whole feature is tenant-safe as-is — every KV key rides `lib/kv.js`'s prefix. Three things need attention under multi-tenancy: (1) `lib/social/carousel-theme.js` hard-codes Vance's palette and the `vancehealthhub.co.uk` CTA domain comes from `BRAND_HUB_DOMAIN` env — both must become **per-tenant** (theme belongs in the tenant's brand record, alongside whatever replaces the hard-coded hexes), and the contrast ratios must be **re-measured per tenant palette**, not assumed, or a tenant with a light brand colour ships an illegible deck. (2) Slides are hosted on the tenant's own WP media library via `WP_SITE_URL`, so this needs the tenant's WP credentials, and a tenant without WordPress has no host — Beta will need a fallback (Vercel Blob or similar). (3) The fixed medical disclaimer on slide 7 is deliberately **not** model-generated; keep it non-editable per tenant, or make it a required per-tenant field — it should never be possible to ship health slides without one. Also note the render is ~450 ms/slide (~4 s/deck) plus 8 sequential WP uploads: at agency volume this wants a queue rather than inline execution inside the automation run.
- **Tag**: #kv #ui #deploy #brand-identity #wizard

## 2026-07-08 — Selectable stock image provider (Pexels ↔ Unsplash), global setting in KV

- **Context**: Added Unsplash as an alternative to Pexels for Stock-Photo heroes, with a global provider toggle + Unsplash Access Key field on the LLM Management page.
- **Finding**: Kept it a **global** setting (not per-category) stored in the existing `vance:hero-prompts` KV record (`stockProvider: 'pexels'|'unsplash'`, `unsplashKey: '<key>'`). `lib/social/media.js` `generateHeroStockImage(title, opts)` gained a provider param with normalised `{url, photographer, sourceUrl}` per provider; `run.js` reads provider+key from the same KV fetch it already does for prompt/source and passes them through. Client manual Auto-Search (`heroLeftSearch`) branches on `heroPromptsConfig.stockProvider`. Unsplash specifics that bit: response shape is `results[]` with `urls.regular` (not Pexels' `photos[].src.large2x`); the API **requires** pinging `links.download_location?client_id=…` when an image is used (done server-side on pick and client-side on select); and the free "demo" tier is 50 req/hr. The access key is a **public** client-side key (same exposure model as the hardcoded Pexels key), so storing it in KV and shipping it to authenticated clients is fine. Because the key lives in KV (entered via UI), automation picks it up with **no Vercel env var needed** — `UNSPLASH_ACCESS_KEY` env is only a fallback.
- **Implication for Beta**: This is another slice of the shared `vance:hero-prompts` KV record — tenant-scoped automatically via `lib/kv.js` prefix. For multi-tenant, each tenant needs its own Unsplash key (they will, since it's per-record). Watch the 50 req/hr Unsplash demo cap under automation volume — a busy tenant needs Unsplash "production" approval or should stay on Pexels. The provider abstraction in `generateHeroStockImage(title, {provider, unsplashKey})` is the extension point if more providers (Pixabay, Openverse) are added later.
- **Tag**: #kv #ui #prompts

## 2026-07-07 — Reading-time + category-prefix must be stripped at generation time, not just at render

- **Context**: User reported the category title prefix ("Clinical Review:" etc.) and the "Reading Time: X minutes" line still showing up, despite existing strip logic. Both are *instructed* by the prompts — category prompts demand a "Clinical Review:" / "Gastro Health News:" title prefix, and the master prompt (+ ibd-living prompt) say "The Reading Time label is the next line."
- **Finding**: The strippers only ran at **render/publish** time (`formatArticleHTML` in index.html, `markdownToWpHtml` in api/publish) and on the extracted **title** field (`extractTitleFromArticle` / automation `stripCategoryPrefix`). The **raw stored body** (`rawArticleText` manual; automation's `body = lines.slice(1)`) still carried a reading-time line, so it leaked into copy/edit/source surfaces. Key automation detail: the title line is split off (`body = lines.slice(1)`), so the body has no H1 prefix — but a reading-time line emitted as the *second* line lands as the first body line. Fix = sanitize at **generation** time in both flows: index.html `sanitizeGeneratedMarkdown()` on `rawArticleText` (drops reading-time lines + strips prefix on first H1); run.js `stripReadingTimeLines()` on `body`. Also removed the reading-time instruction from `MASTER_PROMPT_DEFAULT` and the ibd-living prompt. Caveat that drove the design: the **live** master + per-category prompts are in KV/GitHub, so editing code defaults alone can't stop existing installs emitting these — the generation-time sanitizer is the only prompt-source-agnostic guarantee.
- **Implication for Beta**: Beta inherits the same prompt→KV→strip architecture per tenant. Apply the same generation-time sanitizer; do NOT rely on render-time stripping alone (raw body persists to storage and leaks anywhere that shows source). The known-prefix regex is brand-coupled (`clinical review|gastro living|gastro health news|op-ed|white paper|infographic`) — in a multi-brand/tenant world the prefix set must be per-tenant (derive from the tenant's category labels) or the sanitizer will miss renamed prefixes. Worth closing the loop by also scrubbing the tenant's saved master prompt, not just the code default.
- **Tag**: #prompts #kv

## 2026-07-07 — Per-category hero image source (AI vs Pexels stock), honoured in generator + automation

- **Context**: Added a per-category "Hero Image Source" toggle (✨ AI Generated / 🔍 Stock Photo) in the category editor, so a category's hero can come from Pexels stock instead of AI generation. Previously automation *only* did AI heroes; Pexels lived client-side only (manual generator's Auto-Search).
- **Finding**: Storage rides the existing `vance:hero-prompts` KV record — added a parallel `sources: { [catId]: 'stock' }` map alongside `categories`/`presets`/`default` (only `'stock'` is persisted; `'ai'` is the default and stays out of the map). The `hero-prompts.js` PUT already does partial-merge per slice, so the new map slots in the same way. Server-side Pexels now lives in `lib/social/media.js` as `generateHeroStockImage(title)` (env `PEXELS_API_KEY`, falls back to the same key the client hardcodes) with a local title→keywords helper — no LLM. `run.js` resolves `heroImageSource` once per run next to `heroPromptTemplate` and branches the hero-gen call, keeping the same 90s timeout race; stamps `heroImageType: 'pexels'` (reused the manual flow's existing value rather than inventing `'stock'`, since `heroImageType` is passive display metadata, never branched on). Client: `heroPromptsConfig.sources` cached, `persistCategoryHeroPrompt(catId, text, source)` gained a 3rd arg, and `switchCategory` defaults the manual Hero Image card mode to the category's source.
- **Implication for Beta**: This is per-category config in a *shared* KV record — under multi-tenancy the `sources` map must be tenant-scoped the same way `categories` is (rides `lib/kv.js` `p(key)` prefix, so it's automatic once tenancy lands). Note the Pexels API key is currently a shared hardcoded fallback in both `index.html` and `media.js`; for a multi-tenant/public showcase, move it to env-only and consider a per-tenant key + usage budget (Pexels has rate limits, and one tenant's automation volume shouldn't exhaust a shared key). The manual generator's *AI* path still reads only `heroPromptsConfig.default` (not the per-category prompt) — pre-existing gap, unrelated to this change but worth closing in Beta.
- **Tag**: #kv #prompts #ui

## 2026-06-29 — Shared Upstash Free-tier 500k cap takes the whole app down; surfaces as a login JSON-parse error

- **Context**: Users hit `Unexpected token 'A', "A server e"... is not valid JSON` when logging in. Looked like an auth/login code bug.
- **Finding**: Not a code bug. The single Upstash Redis store (the app's *entire* database, shared across vancecontent + ibdhealthhub + others via `KV_PREFIX`) hit its **Free-tier 500,000 requests/month hard cap**. Every `kv.*` call then throws `UpstashError: ERR max requests limit exceeded`, so functions 500 with Vercel's plain-text `"A server error has occurred"` page — and the client's unconditional `await r.json()` ([index.html](../index.html) `submitLogin`, ~line 13097) turns that into the cryptic JSON-parse error. The crash is at the *first* KV read (`loadUsers` → `kv.get('users')` in [lib/users.js](../lib/users.js)), before any auth logic runs. Diagnosed via Vercel runtime logs (the stack trace names `UpstashError`), not the browser error. The store's Vercel resource name (`upstash-kv-violet-village`) differs from its endpoint host (`nearby-werewolf-76207.upstash.io`) — don't expect them to match. **Fix**: upgrade the store from Free → Pay-as-you-go in the Upstash/Vercel integration (no code change). ~$1–2/mo at this volume. Verify recovery: `curl -X POST .../api/auth/login` returns `401` not `500`.
- **Implication for Beta**: Beta shares this same Upstash architecture and will hit the same shared cap — and worse, in a multi-tenant world one noisy tenant can exhaust the cap for *all* tenants. (1) Keep the store on a metered (non-Free) plan. (2) Consider per-tenant request budgeting once tenancy lands. (3) Add graceful degradation: wrap KV reads so an unavailable store returns `503 {"error":"..."}` JSON instead of crashing into the plain-text page — clients should never `r.json()` a non-OK response unconditionally. `users` is read on *every* authenticated request (`getCurrentUser`) and is a prime caching candidate to cut request volume.
- **Status (2026-06-29)**: Graceful degradation now implemented in alpha and ships forward — `lib/api.js` exports `withErrorBoundary(handler)` + `isKvUnavailable(err)`; applied to the auth handlers, both `[...slug]` catch-alls, and `content` index/[id]. KV outages return `503 {error}`, bugs return `500 {error}`, never plain-text. Client adds `readJsonResponse()` (in `index.html`) used by `submitLogin`/`submitChangePassword` so non-JSON bodies degrade to a clean message. `getCurrentUser` now reads `users` through a 10s per-instance cache (`bustUsersCache()` on every write) to cut the per-request KV volume that contributed to hitting the cap.
- **Tag**: #kv #auth #deploy

## 2026-05-15 — `lib/kv.js` `KV_PREFIX` wrapper is the load-bearing tenancy primitive

- **Context**: Auditing vancecontent for the multi-tenant retrofit (the SCF-Multi-Agency plan).
- **Finding**: Every KV call routes through `p(key) = ${PREFIX}${key}`. A static env var (`KV_PREFIX=vance`) silently namespaces the entire database. This pattern was added as a Hobby-tier cost hack (share Upstash across projects) and is the single most important file for the multi-tenant pivot.
- **Implication for Beta**: Refactoring `p(key)` to read from AsyncLocalStorage instead of a static env var is a one-file change that unlocks request-scoped tenancy for every handler downstream. **Do not** refactor handlers to pass tenant context — just refactor `lib/kv.js`. Phase 1 of the plan.
- **Tag**: #kv

## 2026-05-15 — Vercel catch-all uses `req.query['...slug']` (three literal dots), and subdir handlers hijack it

- **Context**: Reading `api/automation/[...slug].js` for the agency-tenancy wrapping point.
- **Finding**: Two non-obvious things: (1) the query key is the literal string `'...slug'` with three dots, not `'slug'`; (2) any file at `api/automation/rules/index.js` (or similar subdirectory) routes there *instead of* the catch-all, **even if listed in `.vercelignore`**.
- **Implication for Beta**: The catch-all is exactly the right place to add `withTenant()` AsyncLocalStorage wrapping — single entry point for ~25 sub-handlers under `lib/automation/handlers/`. Beta inherits this. **Never** create subdir handler files; keep new handlers inside `lib/automation/handlers/` and import them into the catch-all.
- **Tag**: #routing #ship-pipeline

## 2026-06-02 — Hero image prompts are now KV-backed and per-category

## 2026-06-16 — `ghGetFile` double-decoded the >1MB download_url path ("URI malformed")

## 2026-06-16 — Automation rule had no concurrency lock → duplicate articles per title

- **Context**: A content audit found two articles for one approved title ("Pregnancy and IBD", created 5s apart; also a "Fighting Fatigue with IBD" pair). The daily cron fires once at 07:00, but these were created mid-morning — i.e. from repeated manual "Run now" clicks.

## 2026-07-27 — `margin: 0 auto` inside a flex container makes a page container shrink-wrap and slide sideways

- **Context**: Unifying the six sub-tabs of the Social page. The user reported the page "jumps about" between tabs — the whole content container changed width *and* horizontal position depending on which sub-tab was active, not just the content inside it.
- **Finding**: `.tab-view.active` is `display:flex; flex-direction:column`, so its child `.social-view` is a flex item and its `margin: 0 auto` is an **auto margin on the cross axis**. Per the flexbox spec, auto cross-axis margins suppress `align-self: stretch` — so the box is no longer stretched to the container, it is sized to **fit-content** and then centred in the leftover space. The container's width therefore tracks whatever the visible pane's content happens to demand, and because it is centred, a width change also moves its left edge. Measured at a 1820px viewport: left jumped 454 → 554 → 459 and width 932 → 1133 purely by switching tabs. Adding `width: 100%` makes the used width definite (100%, capped by `max-width`), auto margins then only distribute the leftover, and every tab locks to left=300 / w=1440.
  Three things worth carrying:
  1. **This is invisible below the `max-width` breakpoint.** When the viewport is narrow enough that available < `max-width`, the box fills anyway and looks fine. It only manifests on wide screens — which is why it survived so long, and why reproducing it needs an explicitly widened viewport, not the default one.
  2. **`width: 100%` was already the house pattern** — `.app-container`, `.calendar-view`, `.archive-container`, `.comparison-container`, `.reports-container` all had it. Five containers had silently drifted without it (`.social-view`, `.monitoring-view`, `.llm-page`, `.cats-page`, `.trash-page`). A `max-width` + `margin: 0 auto` container inside a flex parent is only correct *with* the explicit width; treat a missing one as a bug, not a style choice.
  3. **Uniformity is vertical too.** Panes whose subtitle wrapped to 1 vs 3 lines started their content up to 36px apart, so switching tabs jumped the page even with the container locked. A `min-height` on the shared pane header (sized to the 2-line case) pins the body to the same y on every tab — but it only holds if the copy actually fits two lines, so subtitle length becomes a design constraint, not free text.
- **Implication for Beta**: Beta inherits this whole shell, and the agency layer adds *more* tab-like surfaces (per-tenant views, tenant switcher) hanging off the same `.tab-view` flex pattern — so any new `max-width` + `margin: 0 auto` wrapper will reproduce the bug the moment a tenant's screen is wider than the cap. Worth turning into a shared `.page-container` class rather than repeating the three declarations per view, since the failure is silent on the developer's own monitor and only shows up on a customer's ultrawide. The `min-height` pane-header convention should also be encoded once centrally: with per-tenant copy (tenant-authored titles/subtitles) the two-line assumption is no longer under our control, so Beta likely needs a line-clamp on the subtitle as well as the `min-height`.

## 2026-07-29 — A capped index shared by two producers is a race between them, and losing it is silent

- **Context**: Adding scheduled promotional carousels alongside article carousels. Both kinds are ordinary deck records and both were registered in the same capped KV list, `social:carousels:index` (`lpush` + `ltrim` to 200).
- **Finding**: One capped list shared by two producers means the *faster* producer sets the retention window for the *slower* one. Articles arrive at roughly 10/week; a daily promo campaign adds 1/day, so within about seven months every article deck would have been trimmed off the end. The failure mode is what makes this worth writing down: **nothing breaks and nothing is deleted**. What operators actually want to vary turned out to be entirely microcopy — the two slide labels, the disclaimer, the button text — which is both safe and sufficient. So the override surface is exactly six string fields, and the base style still owns grounds and colours. Two implementation details worth carrying: (1) **`''` and absent must stay distinguishable** — a template setting `disclaimer: ''` means "omit the disclaimer", which is a *different instruction* from "inherit the base style's", so the merge uses `in` checks rather than `??`, and the UI models it as a three-way select (inherit / none / custom) rather than a text box where blank is ambiguous; (2) **the resolved theme is stamped onto each deck at mint time, not resolved at render time** — a template edit should reach campaigns from their next occurrence but must never silently rewrite a deck already rendered, hosted and possibly posted. Same reasoning that already applied to `spec`. Built-ins are *derived* from the style map rather than seeded into KV, so there is no stored copy to go stale when a style changes, and they are read-only by construction — the handler returns 400 with a reason rather than 404, and the editor pre-fills a copy instead of refusing, because "Education cannot be edited" is a useful answer and "not found" is a baffling one for something the picker just showed you.
- **Also from this batch**: the server-side stock search added here closes the client-side Unsplash key exposure recorded in the 2026-07-21 entry, but only for this path — the article hero picker still calls `api.unsplash.com` from the browser. Two guideline details that are easy to get wrong: the download endpoint must be pinged when a photo is **used**, not when it appears in results (pinging on search inflates every photographer's download count with photos nobody chose), and the required credit link is `user.links.html` (the photographer's profile), not `links.html` (the photo page). Also: the Pexels key was a hardcoded literal inside `media.js`; it is now exported rather than copied into the new handler, because a duplicated credential gets rotated in one place and quietly keeps working in the other until it does not.
- **Implication for Beta**: templates are the natural per-tenant customisation point, and this constraint is what makes them safe to expose to tenants at all — an agency client can rebrand the wording without being able to produce an inaccessible deck under someone else's brand. Beta should keep the override surface to strings and add per-tenant *palettes* as a separate, reviewed artefact rather than a free-text colour field on a template. The stock-search proxy should be platform-level with per-tenant keys and per-tenant rate accounting, since Unsplash's demo tier caps at 50 req/hr for the whole app: on a shared key, one tenant's image browsing silently exhausts every other tenant's budget, and the 403 that follows says nothing useful.

## 2026-07-29 — Navigation debt is easier to remove than to explain, but the removal is where the runtime errors live

- **Context**: Consolidating the app's navigation. Six asks in one pass: build the empty Social ▸ Posted pane, give every queued post its own controls, regroup the Social tabs by stage, merge Prompt Library with Connections, merge Approval Log with Notifications into "Operations Logs", and delete Monitoring, Reports and the whole AI document-comparison feature.
- **Finding**: Three things generalise from this.
  1. **A "coming soon" stub is a data-model question wearing a UI question's clothes.** `loadSocialPosted()` had been a one-line placeholder for as long as the pane existed, and the reason was not effort — it was that no single index sees every posted item. `social:posted:index` only ever received entries from the cron drain, so a deck sent via **Post now** or an `immediate` post mode was live on Instagram and invisible in the app forever. The feed now merges three sources (posted refs, every carousel carrying a `postedAt`, and kit platforms with a `postedAt` from before the index existed), de-duplicating on `carousel:{id}` / `kit:{kitId}:{platform}`. The real fix was upstream: `postCarouselNow()` now registers into the posted index and mints the post ref if none exists, so the bypass path stops being invisible. **When a write path bypasses the queue, check that it also bypasses the queue's bookkeeping.**
  2. **Pause has to live somewhere, and "somewhere" cannot be the queue.** The social cron reads `social:queue` (a sorted set scored by `scheduledAt`), so the only way to stop a post firing is to remove it from that set — which is also the only way to stop it appearing in the queue list. A paused post therefore needs a second index (`social:queue:paused`) purely so it can stay on screen while being off the clock. Resume deliberately does **not** restore a slot that has already passed (it pushes a minute out), because "resume" a week later meaning "post immediately on the next sweep" is never what the operator intended. Every carousel-kind mutation also has to mirror onto the deck record — pausing a queued deck without moving it off `scheduled` leaves the Instagram pane insisting it is going out when nothing is armed to send it.
  3. **Deleting a feature is mostly deleting its call sites, and the call sites are where it breaks.** Removing the comparison feature took ~450 lines of markup, JS and CSS, but the breakage risk was entirely in six survivors: `updateCompareBar()` calls scattered through legacy archive helpers, `renderReports()` called from two category-switch paths, a bare `document.getElementById('reportsStats').textContent = …` that throws the moment the element is gone (the sibling `archiveStats` call had the same shape and had simply never been exercised without its element), a `ghData[cat].comparisons` slot feeding a dashboard stat, a GitHub file fetched on every sync for data nothing read any more, and a poller line refreshing a tab that no longer exists. **Grep for the removed symbols, then grep again for the DOM ids they touched** — an unguarded `getElementById(...).textContent` is a runtime error, not a dead branch.
- **Also from this batch**: retired routes were kept as an explicit `RETIRED_TABS` redirect map rather than deleted, because `tabFromHash()` resolves validity by checking whether `view-{tab}` exists — so a bookmarked `#approval-log` would have silently landed on the dashboard with no indication anything had moved. And `apiFetch` was throwing the raw response body, so every handler's carefully-worded `{ error: "…" }` reached the user as JSON; it now unwraps `.error`, which matters much more once the UI has buttons whose failure messages are the only feedback.
- **Implication for Beta**: Beta clones this navigation, so it inherits both the consolidation and the redirect map — worth taking the redirects rather than re-deriving them, since Beta's tenants will have their own bookmarks. Two Beta-specific notes: the posted feed reads `automation:rule:{id}` to resolve rule names for its filter facets, which under multi-tenancy must be scoped or a tenant sees another tenant's rule names in a dropdown; and `social:queue`, `social:queue:paused` and `social:posted:index` are all global keys in the same family already flagged in the capped-index entry above — the queue actions added here (pause / reschedule / post-now / trash) act on a post ref id with **no ownership check at all**, which is fine for a single owner-operated brand and is a straightforward cross-tenant write on an agency platform. That authorisation check is a prerequisite, not a follow-up.

## 2026-07-29 — "Connected in Composio" is not one thing, and a generated count is not the user's count

- **Context**: Closing the last client-side stock-API key exposure, widening promo decks to 1-10 slides, and wiring Canva in as a slide source after the user connected it to Composio.
- **Finding**: Three things, each a different shape of the same mistake — trusting something that looked authoritative.
  1. **A toolkit connected through an AI assistant's Composio connector is invisible to the app**, even though both are "Composio". They are separate projects with separate API keys and separate user scopes; the id formats differ visibly (`ca_xRKJzsuKun3K` for the app's own connections versus `canva_banal-turken` for the connector's). No code change can bridge them: the app needs its own Auth Config for the toolkit and its own `link()` flow. **Worth checking the id shape before concluding an integration is broken** — and worth having the status endpoint name the three failure modes separately (no Composio key / no Auth Config / configured but nothing connected), because they have three different fixes and a single "not connected" message sends someone to the wrong one.
  2. **The model's output silently overrode the operator's setting.** Promo decks gained a 1-10 slide control, and asking for 5 produced 8: the prompt requested 1 point slide, the model returned 4, and both the spec builder (`points.length + FIXED_SLIDES`) and `planSlides` derived the deck length from what came back. That derivation was correct when the range was a fixed 6-10 and the count was implied by the points; it became a bug the moment the count became an explicit user choice. **When a setting moves from implied to chosen, every place that used to infer it has to be re-audited** — inference that was previously the source of truth is now a competing one, and the user's choice must win. Caught only by testing each count end to end, because the deck still rendered perfectly, just at the wrong length.
  3. **1 slide is not a small carousel.** Instagram's carousel endpoint requires 2..10 children, so a one-slide deck has to publish through the single-image path. There was already a cover-only fallback for when carousel posting fails, and reusing it would have been a one-line change — but it flags results `degraded`, which means "we wanted a carousel and could not manage one". Reusing the mechanism while inheriting the wrong semantics would have made every deliberate single-image post look like a failure in the logs. Same code, renamed and called from two places with different meanings.
- **Also**: the article hero picker's Unsplash key finally moved server-side, which required adding `page`/`hasMore` to the shared stock endpoint. One knock-on worth noting: the endpoint now returns UTM-tagged profile links, so the client's credit renderer had to become idempotent — it had been appending the parameters unconditionally, which would have doubled them on every new pick while leaving older saved credits correct.
- **Implication for Beta**: the Composio-project distinction is a support burden waiting to happen under multi-tenancy — tenants will connect toolkits in whatever Composio they are already logged into, and Beta needs the same three-state diagnostic per tenant plus an explicit "this is the project you must connect to" identifier surfaced in the UI. The slide-count lesson generalises to every per-tenant setting Beta adds on top of alpha's defaults: alpha frequently derives values that Beta will want to expose as choices, and each one needs the derivation replaced rather than merely overridden. And on Canva specifically: the capability flag (`brand_template`) being present does not mean brand templates exist — this account had the capability and zero templates, so any tenant-facing UI must distinguish "your plan cannot" from "you have not made one yet".

## 2026-07-29 — Getting house styles into Canva as editable text, and where the brand-template path actually stops

- **Context**: Pushing the three editorial carousel styles (education, relatable, breaking-news) into Canva as designs an operator can improve by hand, then publishing them as brand templates so the `canva-template` autofill renderer has something to fill. The account had `brand_template` capability and zero templates, which is where the previous entry left it.
- **Finding**: Five things, roughly in order of how much time each would cost to rediscover.
  1. **Never export the app's renderer to get an editable file.** Satori outlines every glyph to paths on the way to SVG, so anything the carousel pipeline produces is flat artwork with no text. The only honest route is to rebuild the deck from the theme constants in whatever format the target understands. That is not duplication for its own sake: `scripts/build-canva-style-decks.mjs` imports `C`, `MUTED`, `TYPE`, `PAD`, `STYLES` and the rest from `lib/social/carousel-theme.js`, so the Canva copy cannot drift from the renderer's design system without someone editing the shared source.
  2. **Canva's HTML import is a better path than `.pptx`, and needs no dependency.** One `data-document-role="page"` element per slide, sized in CSS, imports as a genuine page with real text boxes at the right size, weight and letter-spacing (px letter-spacing arrives as em, correctly converted). Crucially the pages come in as **FIXED**, which is the precondition for autofill tagging — responsive pages reject `update_autofill_field` outright. Hosting is the only friction: the importer demands a public HTTPS direct-download URL, which for this repo means deploying the files to Vercel, importing, then deleting them and redeploying.
  3. **The importer drops alpha on text colours and lands on `#000000`.** Every `rgba()` muted colour in the theme came through as black, which put black body text on the navy ground. The fix is to composite the alpha against its known opaque ground before emitting the HTML, which is not an approximation — alpha over a known ground is exactly the calculation the measured contrast ratios in `carousel-theme.js` assume, so `#BFC6CF` on ink is the same pixel the renderer produces and holds the same 7.38:1. **Any export path out of this design system has to flatten `MUTED` first.**
  4. **Brand templates CAN be created programmatically now, but not through Composio.** The long-standing belief that publishing a brand template is UI-only is out of date: Canva's own MCP connector exposes `publish-brand-template`, plus an `update_autofill_field` edit operation that names the autofill fields. Composio's Canva toolkit has no equivalent — it is list, autofill, designs and exports only — so the app itself still cannot do this, and the capability arrives via a connector rather than via the integration the app uses.
  5. **Where it stops: `publish-brand-template` fails with `Missing scopes: [brandtemplate:content:write]`** unless the Canva connector is disconnected and reconnected to mint a token carrying that scope. Worth knowing before planning around it, because everything upstream (import, tag, commit) succeeds and the failure only surfaces at the last call.
- **Also worth recording**: two identity checks that are easy to get wrong. Composio and the Canva connector report **different** opaque `user_id`/`team_id` values for what is demonstrably the same Canva account, because those ids are scoped per OAuth client — so **comparing them is not a valid way to test whether two integrations point at the same account**. Comparing the returned design id lists is: identical ids in identical order is direct evidence. Separately, `POST /api/social/promos/preview` accepts an unsaved campaign in its body, so verifying a renderer end to end needs no create-then-delete cycle and persists nothing.
- **Implication for Beta**: the export-to-editable problem is exactly the shape of a feature agency tenants will ask for ("give me our template in Canva / Figma / PowerPoint"), and the answer must always be regenerate-from-tokens, never export-the-renderer — so `carousel-theme.js`'s constants should be treated as Beta's public design-token API, with per-tenant themes flowing through the same flattening step. The scope failure matters more under multi-tenancy: a tenant can connect Canva successfully, browse designs, autofill existing templates, and still be unable to publish one, so Beta's Canva status endpoint should report **write** capability separately from connection state rather than inferring "connected means usable". And the ids-are-per-client finding is a trap for any Beta code tempted to reconcile a tenant's connectors by matching account identifiers.

## 2026-07-29 — The Canva autofill renderer had never actually run, and two bugs were waiting in it

- **Context**: Immediately after the entry above. The connector was reconnected with `brandtemplate:content:write`, all three house-style decks were published as brand templates, and the `canva-template` renderer was exercised end to end for the first time.
- **Finding**: The renderer could not have worked as shipped. Both defects are the same species — code written against a plausible mental model of an API, never executed against it.
  1. **Two async jobs with identical response shapes are not the same endpoint.** `autofillBrandTemplate` polled `CANVA_GET_DESIGN_EXPORT_JOB_RESULT` (`/v1/exports/{id}`) for an autofill job, which lives at `/v1/autofills/{id}`. It failed 403 `permission_denied` every time. The code's `job.result.design.id` read was already right, which is exactly why the bug survived review: the shape matched, so reusing the export poller looked like sensible deduplication. The correct slug is `CANVA_RETRIEVE_DESIGN_AUTOFILL_JOB_STATUS`.
  2. **The brand-template LIST endpoint does not include the dataset.** `listBrandTemplates` mapped `t.dataset`, which is never present — the list returns only id/title/thumbnail/urls, regardless of the `dataset=non_empty` filter it accepts. So `fields` was always `[]`, the campaign stored `canvaFields: []`, and autofill died on "None of the brand template's field names matched". Composio exposes no equivalent of Canva's `/v1/brand-templates/{id}/dataset`, so **the field names are not discoverable through Composio at all**.
  3. **The fix that unblocks it: Canva's autofill ignores undeclared keys.** Verified rather than assumed, by autofilling a live 14-field template with a deliberately bogus key and getting a successful 8-page design back. So an empty field list is treated as *unknown* rather than *none*, and `buildAutofillData` sends every name it holds. That is a legitimate design, not a hack, precisely because the API is documented-by-experiment to be tolerant — but it only works if the candidate names are in their **canonical spellings**, since Canva matches exactly and the old mapper stored normalised keys (`hooktitle`) that would never match a real `hookTitle` field.
  4. **Composio's semantic tool search is not a reliable index of its own toolkit.** `CANVA_RETRIEVE_DESIGN_AUTOFILL_JOB_STATUS` was never returned by any phrasing of "autofill job status"; searching returned asset-upload tools instead. It was found by guessing a slug name and reading the "did you mean" suggestion from `COMPOSIO_GET_TOOL_SCHEMAS`. **When a Composio tool ought to exist, probe the schema endpoint with guessed slugs before concluding it does not.** The same probe returned no suggestion for a brand-template-dataset slug, which is what made "it genuinely does not exist" a safe conclusion rather than a guess.
  5. **`publish-brand-template` reports failure on success.** It creates the template, then errors reading it back: `Not allowed to access brand template with id 'EA…'`. Retrying on that error publishes duplicates. Always check the id in the error message with `get-brand-template-dataset` before retrying.
  6. **Fixed pages do not reflow, so autofill overruns any box sized to its placeholder.** Canva's import freezes flow layout into absolute positions. A cover headline box laid out around the single word "hookTitle" was rendered straight over the swipe hint the moment a three-line headline was autofilled. Any generated template must **reserve** the space its longest realistic copy needs, not the space its placeholder happens to occupy.
- **Also**: `POST /api/social/promos/preview` requires the campaign nested as `{"promo": {...}}`; a flat body silently builds a default campaign and fails with a misleading "needs a campaign brief, a CSV message or a topic". And every `canva-template` preview mints a real Canva design, because that is what autofill does — `dryRun` protects KV and WP but not the Canva account.
- **Implication for Beta**: the generalisable rule is that an integration path nobody has executed is not an integration, and both bugs here were in the *second half* of a flow whose first half worked, which is where Beta's risk concentrates too — connection status and listing are exercised constantly by the UI, while the once-per-occurrence job-polling and payload-building code is exercised only by real runs. Beta should have a smoke path per renderer that actually mints one deck, not just a connection check. The undeclared-key tolerance also gives Beta a cheap tenant-facing story: tenants can name their template fields from a published list and anything they omit is simply skipped, so the picker never has to read a dataset it cannot fetch. And the reserve-space lesson applies to every per-tenant template Beta generates: placeholder-sized boxes look correct in the editor and break on first real content.

## 2026-07-29 — Autofill has no draw time: themed defaults must be resolved before the payload

- **Context**: First smoke test of a real published house template (education, `EAHQyMbCWZc`) through `POST /api/social/promos/preview`. Everything filled correctly except the CTA chip, which read literally "CTA" — the placeholder text.
- **Finding**: `cta.label` is campaign config, never model output, and it is empty unless the operator sets it. The satori renderer hides that emptiness by resolving a fallback chain at draw time (`cta.label || theme.ctaLabel || FIXED_COPY.ctaLabel`, so a promo deck gets "SHOP THE RANGE"). The Canva path has no draw time: `buildAutofillData` skips empty values (correctly — sending empty text would blank the field), the field goes unfilled, and an unfilled autofill field keeps whatever placeholder text the template carries. So the two renderers disagreed exactly where the satori path looked fine. Fix: resolve the same fallback chain in `canvaSlideUrls` before building the payload. The general rule: **any value the satori renderer defaults at draw time must be defaulted before autofill**, because a template is filled once and never re-evaluated.
- **Implication for Beta**: every themed default in `carousel-theme.js` is a latent divergence between renderers. When Beta adds per-tenant themes or new renderer targets, audit `FIXED_COPY` and the style overrides for values that reach the spec as empty strings and are only made whole at render — each needs the resolution hoisted to spec- or payload-build time on any path that is fill-once rather than draw-time.

## 2026-07-29 — Editing a published brand template: the draft API is broken, ids churn, and title-search is a trap

- **Context**: Widening the CTA chip on the three freshly published house templates (the chip had been shrink-wrapped around its 3-letter placeholder — the reserve-space rule violated in one spot — and the first real autofill overflowed it).
- **Finding**: Three things about the edit-and-republish path, learned the expensive way across parallel agent runs.
  1. **`create-brand-template-draft` is permission-denied on every template**, including templates the same connector published minutes earlier ("User does not have permission to access brand template with id 'EA…'"). It is the draft-side sibling of the publish false-error: the connector's token can create and fill templates but cannot read them back as drafts. The cycle that works is `create-design-from-brand-template` → `edit-design` → commit → `publish-brand-template`, and crucially **the copy retains the autofill tags** (`dataFieldLabel` on elements), so nothing needs re-tagging.
  2. **Template ids are not stable across edits.** Every publish mints a new EA id; the old template survives unchanged and there is no delete API. So a template revision is really: publish new id, repoint every stored `canvaBrandTemplateId`, delete the old template in the UI. Two of these in the account at once means the picker shows same-titled duplicates until the UI cleanup happens.
  3. **Never resolve a template to "the design with the same title".** Two agents, blocked by finding 1, each independently grabbed the identically titled design from search-designs — which was the stale logo-less duplicate — edited it faithfully, and published junk (one 0-field template, one 2-field). Same-title designs are ancestors, not drafts. The only safe editable copy of a published template comes from `create-design-from-brand-template` on that template's id. A bonus consolation: `dataset=non_empty` on the brand-template list verifiably filters 0-field templates out of the picker server-side, so fully-untagged junk hides itself; partially-tagged junk does not.
- **Implication for Beta**: template-id churn is the structural one — Beta must treat `canvaBrandTemplateId` as a mutable pointer with a repoint-on-revision workflow (and stale-id detection: a campaign whose template id no longer appears in the list should surface a warning, not fail at autofill time). The title-resolution trap is a prompt-engineering lesson for any agentic Canva work Beta automates: pass ids, forbid title lookup explicitly, and say what to do on failure (stop, not improvise).
- **Tag**: #social #brand-identity #agents
